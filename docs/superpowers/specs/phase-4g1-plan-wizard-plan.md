# Phase 4G.1 — Plan Wizard Completion, Recovery & Truthfulness Audit (PART 2: Design Decision)

Decisions are explicit and opinionated. Backend remains authoritative; the FE must
reconcile to it, never guess.

---

## 1. Terminal source of truth for create-plan

**Hybrid: WS for live progress, REST for completion authority.**

- WS frames drive the live progress list and the transient "collecting/running"
  experience.
- **Completion/failure is decided by reconciling to the backend via REST**, because
  the terminal `migration_id:N` WS frame is sent **once**, **after** `runner.Plan`
  returns, and is **not replayable**. A refresh or disconnect before that frame means
  the FE can never rely on the WS alone.
- Concretely: when the WS closes, the FE immediately enters a `checking` state and
  calls the reconciliation endpoint instead of trusting "I saw the frame" or "I
  didn't see the frame". The backend list/get is the truth.

This removes the FE's dependence on a single fragile frame — the direct cause of the
reported bug.

## 2. Primary recovery identifier

**Client-generated `operationId` (UUID), persisted early, plus `migrationId` once known.**

- `operationId`: generated by the FE **before the first submit** (so it survives even
  a double-click/refresh). Sent in `PlanRequest.operationId`. Returned on every
  terminal frame and on the REST row.
- `migrationId`: backend-assigned, surfaced via the terminal frame and the REST row;
  used for navigation once confirmed.
- Why `operationId` and not `draftId`/`migrationId` alone:
  - `draftId` is unused (no draft system exists) — rejected as YAGNI.
  - `migrationId` does not exist until `CreateMigration` inserts, so it cannot guard
    a refresh that happens *before* insertion — rejected as a sole key.
  - `operationId` is stable from first click, survives refresh, and lets the backend
    dedup. **Chosen.**

Persistence (all of these, minimal needed):
- URL query param `?op=<uuid>` — survives refresh + back/forward + shared links.
- `sessionStorage['meshium_plan_op']` — survives refresh within the tab; cleared on
  navigation to the created migration or explicit dismissal.
- The PlanRequest signature (`sourceServerId/targetServerId/categories`) is a
  **fallback** reconciliation key when `operationId` is not yet known server-side.

## 3. Recovery model after refresh

On `onMount`, the wizard checks the recovery token (`?op=` then `sessionStorage`):
- **No token** → fresh wizard at Step 1 (existing behavior).
- **Token present + `planning` not yet confirmed** → restore to **Step 4** in a
  `checking` / `reconnecting` state ("Checking plan status…"), then reconcile:
  1. `GET /api/migrations?operationId=<id>` → if a row exists:
     - status in (`planned`, `running`, `interrupted`) → migrate has been created:
       navigate to `/migrations/{id}/pipeline` (the plan is usable; wizard is done).
     - status `failed` → show terminal failure + safe retry.
     - status completed/committed/etc → navigate to pipeline/detail.
  2. If `?op=` unknown to backend but the request signature matches a recent row
     (fallback) → treat as the same recovery.
  3. If nothing found and `checking` times out → **explicit `unknown`** state with the
     guidance: "Plan status could not be confirmed. Your plan may already exist —
     check Migration History." + a link.
- **Token present but `planning` already confirmed earlier in this session** →
  navigate directly to the created migration (no re-check).

The wizard **never silently returns to Step 1 while a token exists**.

## 4. Anti-duplicate strategy

- **Idempotency key timing:** `operationId` generated in `startPlanning()` *before*
  `wsPlan` is opened, persisted immediately to URL + sessionStorage.
- **Key persistence:** URL `?op=` + sessionStorage.
- **Backend dedup:** `CreateMigration` gains an `operation_id` column. When a
  `PlanRequest.operationId` is supplied and a row with that op exists in a recoverable
  status (`planned`/`running`/`interrupted`/`failed`), the handler returns the
  **existing** migration instead of inserting a new one. (True duplicate plans are
  thereby impossible for a retry/refresh/reconnect.)
- **Double-submit guard:** the Step-4 submit button is `disabled` whenever
  `planning` or a `pending`/`checking` state is active; `startPlanning` is a no-op if
  already in flight.
- **Safe retry:** the Retry CTA is shown **only** in an explicit terminal-failure
  state; retry reuses the **same** `operationId` (so it dedups rather than inserts).
- **Refresh protection:** because `?op=` is in the URL before submit, a refresh while
  running reconciles to the existing migration rather than opening a new plan.

## 5. Backend contract changes (minimum, truthful)

Required (proven insufficient per PART 1 §H):

1. **`operation_id` column** on `migrations` + `OperationID` on `PlanRequest` and on
   `MigrationResponse`/`MigrationPlan`. Accept it; on create, dedup against an existing
   recoverable op.
2. **Reconciliation endpoint:** `GET /api/migrations?operationId=<id>` returns the
   matching migration (or 404/empty). Reuses `handleList` filtering — no new
   status surface area.
3. **Terminal frame carries `operationId`:** `handlePlanWS` includes
   `operationId` in the `migration_id:N` frame so the FE can pair id↔op without
   regex gymnastics. (Keep the `migration_id:N` text for backward compat.)
4. **Make the id-less planner frame non-terminal:** the `WSMessage{step:"plan",
   status:"complete", Value:"Migration plan created"}` at planner.go:229 is emitted
   *before* the migration id is known. The FE must **not** treat a `plan/complete`
   frame without a parsed migration id as completion. Simplest honest fix: change that
   in-progress frame to `status: "progress"` (it is not terminal) so the only
   `complete` that ends the flow is the handler's id-bearing one. The id-bearing
   terminal frame is unchanged.

**Not added:** no second status endpoint, no draft system, no sequence/replay on
`/ws/plan` (WS reconnect is unnecessary once completion is REST-authoritative and the
terminal frame is id-bearing — YAGNI; reconnect would add fragile surface for no
truth benefit the REST reconcile doesn't already give).

## UX state machine (PART 3 §E)

`connecting` → `collecting`/`running` → (`reconnecting` → `checking`) → one of
`completed` | `failed` | `unknown`. Rendered in **words**, not spinner-only. `unknown`
is a first-class terminal state, never an indefinite spinner.

## STOP CONDITION check

- Backend **can** identify an in-flight/completed plan (new `operation_id` + existing
  status). ✅
- Contract **can** distinguish running vs completed vs unknown (`status` already does;
  `failed`/`interrupted` already exist). ✅
- Duplicate prevention **can** be guaranteed (op-keyed dedup + double-submit guard). ✅
- Refresh recovery **can** be truthful (op in URL + REST reconcile). ✅
→ Continue to PART 3. No STOP triggered.
