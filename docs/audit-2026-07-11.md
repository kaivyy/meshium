> Audit grounded in actual code (file:line cited throughout), not theory.
> Conducted across 5 parallel passes: backend architecture, DB adapter,
> transfer engine, replication/cutover, frontend/observability.
> Date: 2026-07-11. Codebase state: post beta.9.

# 1. Executive Assessment

## Masalah desain paling kritis

1. **Zero-downtime tidak benar-benar terdeliver.** Seluruh infra cutover
   (`CutoverEngine`, `TrafficSwitchEngine` 7 provider, `FreezeManager`,
   `ObservationEngine`) sudah diimplementasi tapi **zero live caller**.
   `trafficSwitchStage` (`pipeline.go:1662-1725`) hanya menulis
   `"manual_required"` lalu lanjut ke `StateCommitted`. Replication setup
   jalan, tapi traffic switch manual. `pipeline.go:1640-1658`.

2. **Split-brain pada rollback replication.** `rollbackMySQL`
   (`replication.go:319`) `STOP SLAVE; RESET SLAVE ALL` — target jadi primary
   writable, source juga masih primary (tidak pernah di-demote). Dua writer.
   `rollbackPostgreSQL` (`replication.go:424`) `rm standby.signal` pada standby
   yang di-stop = **promote** target, bukan demote. Critical.

3. **Checkpoint tidak pernah dipersist.** `UpdateStageCheckpoint`
   (`pipeline_repo.go:148`) punya **zero caller**. Stage data ditulis ke
   `pc.CheckpointData` map in-memory (`pipeline.go:1048,1077`) lalu hilang saat
   crash. Kolom `checkpoint_data` selalu NULL. Resume hanya granularitas stage,
   bukan mid-stage (kecuali `initialSyncStage` via `StepStatusApplied`).

4. **Large-file transfer tidak viable.** SFTP `FileTransfer` timeout 5 menit
   (`ssh/model.go:29`, `ssh/client.go:713,758`) — file >~3GB@10MB/s pasti
   timeout. `ExecContext` buffer stdout penuh (`ssh/client.go:361 bytes.Buffer`)
   — rsync remote-to-remote & SyncEngine checksum OOM. Docker volume via
   tar+SFTP (`planner/bridge.go:264`), 5-min timeout, path tidak di-shell-quote
   (injection). `ExecWithStdin` streaming restore pakai timeout Command 30s
   (`ssh/client.go:647`) — restore >30s terbunuh.

5. **DB container: silent skip, bukan error.** Tidak ada field `container`
   (`database_adapter.go:76-85`). `Detect` pakai `pgrep` di host shell — DB
   dalam container tidak kelihatan → `Collect` return `{}` no-op → plan
   "sukses" dengan 0 DB termigrasi. User tidak diberi tahu.

6. **Rollback always `StateRolledBack` walau gagal.** `rollbackPipeline`
   (`pipeline.go:983-1001`) log error tapi final state selalu `StateRolledBack`
   (line 1005). Manual `Rollback()` benar (`StateRollbackDegraded`), tapi path
   otomatis menutupi kegagalan rollback parsial.

## Risiko terbesar (urut)

| # | Risiko | Severity |
|---|--------|----------|
| 1 | Split-brain rollback replication (dual primary) | **Critical** |
| 2 | Cutover/traffic/freeze dead code — zero-downtime palsu | **Critical** |
| 3 | Checkpoint tidak persist — resume mid-stage tidak mungkin | **High** |
| 4 | SFTP 5-min + ExecContext OOM — file >3GB & DB restore >30s gagal | **High** |
| 5 | MySQL `Detect` always-true (`;` bukan `&&`, `database_adapter.go:238`) | **High** |
| 6 | Redis restore `|| true` mask kegagalan restart, Redis bisa mati | **High** |
| 7 | Redis password di argv (`-a`), visible di `ps` target | **Medium** |
| 8 | Mongo pakai `mongo` legacy shell, absen di Mongo 6+ | **Medium** |
| 9 | `ForceTransition` merusak state machine di setiap error/rollback path | **High** |
| 10 | Volume path tidak di-shell-quote (`planner/bridge.go:266,279`) | **High** |
| 11 | Correlation ID dead code — semua event `correlationId: ""` | **Medium** |
| 12 | `log.Printf` unsanitized di executor.go (16 call sites) | **Medium** |

## Prioritas rekomendasi

- **P0 (block release):** Fix split-brain rollback (#1), Redis `|| true` (#6),
  MySQL Detect (#5), volume injection (#10), ExecWithStdin 30s (#4 partial).
- **P1 (MVP correctness):** Persist checkpoint, SFTP timeout configurable +
  streaming untuk dump/restore, container mode adapter.
- **P2 (zero-downtime real):** Wire `CutoverEngine` + `FreezeManager` +
  fencing, atau honest "manual cutover" state tanpa auto-advance.
- **P3 (hardening):** Correlation ID, structured logging, dead code cleanup,
  `ParallelTransfers`/`BandwidthLimit` wiring, `mongosh`.

## Context + retry design

```go
func withRetry(ctx context.Context, max int, fn func(context.Context) error) error {
    backoff := time.Second
    for attempt := 0; attempt < max; attempt++ {
        if ctx.Err() != nil { return ctx.Err() }
        if err := fn(ctx); err == nil { return nil } else if !classify(err).Retry() { return err }
        select {
        case <-time.After(backoff):
        case <-ctx.Done(): return ctx.Err()
        }
        backoff *= 2
    }
    return last
}
// Rollback uses context.Background() — must NOT inherit cancelled ctx.
// (Current bug: pipeline.go:920 uses pipeline ctx for rollback.)
```

## Apakah field `container` cukup?

**Tidak cukup tunggal.** Cukup untuk container sederhana, tapi Compose butuh
service+file. Rekomendasi: **abstraction executor/transport** lewat `ExecMode`
+ `Container`/`ComposeSvc`/`ComposeFile`. Command builder pilih prefix:

```go
func (c DatabaseConfig) wrap(cmd string) string {
    switch c.ExecMode {
    case ExecContainer:
        return fmt.Sprintf("docker exec -i %s %s", shellQuote(c.Container), cmd)
    case ExecCompose:
        return fmt.Sprintf("docker compose -f %s exec -T %s %s",
            shellQuote(c.ComposeFile), shellQuote(c.ComposeSvc), cmd)
    default:
        return cmd
    }
}
```

Streaming tetap jalan: `docker exec -i` pipe stdin/stdout. **Jangan `-t`**

# 5. Large File Transfer Engine

## Pilihan strategi berdasar ukuran/network

| Ukuran | Network | Strategi |
|--------|---------|----------|
| <1 GB | LAN cepat | tar over SSH atau SFTP |
| 1–50 GB | LAN | **rsync --partial --append-verify** |
| 50–500 GB | WAN lambat | **rsync + zstd + split chunk** resumable, atau rsync direct src→dst |
| Docker volume besar | any | **rsync over SSH** antar host, bukan tar+SFTP via meshium |
| DB dump | any | stream pipe, nol temp |

## Resume/checkpoint

```
1. Persist TransferCheckpoint{file, bytesTotal} sebelum transfer.
2. rsync --partial --append-verify: native resume byte offset.
3. Post: sha256sum source==dest. Persist checksum.
4. Retry: load checkpoint, rsync lanjut (bukan from zero).
5. SFTP path: GANTI ke rsync untuk >1GB (SFTP resume korup, scp.go:319).
```

## Checksum

- Stream (`io.Copy(hash, file)`) — tidak OOM. Aman.
- Remote `sha256sum` via `ExecContext` — **BUG:** timeout Command 30s bunuh
  proses untuk file >~10GB. Fix: jalankan tanpa timeout via `ExecPipe`.
- Bandingkan source==dest, retry 3x mismatch, lalu fail.

## rsync vs tar+zstd+ssh vs chunked

| Strategi | Resume | Checksum | CPU | Kapan |
|----------|--------|----------|-----|------|
| **rsync --partial** | ✅ native | ✅ | rendah | **default** |
| tar+zstd\|ssh | ❌ zero | manual | tinggi | banyak file kecil, network cepat |
| chunked + paralel | ✅ per-chunk | ✅ | sedang | >200GB, WAN tidak stabil |
| SFTP (sekarang) | ⚠ korup | ❌ timeout | rendah | hanya file kecil |

**Default: rsync.** Streaming pipe untuk DB. Chunked hanya Phase 2.

## Kompresi: kapan cepat vs lambat

| Tipe file | Kompres? | Alasan |
|-----------|---------|--------|
| DB dump (text) | ✅ | 3-10x |
| Docker image/layer | ❌ | sudah terkompresi |
| Video/gambar | ❌ | sudah terkompresi |
| node_modules | ⚠ | overhead > gain |
| Archive | ❌ | double-compress waste |
| Log/config | ✅ | compressible |

**BUG:** `transfer/rsync.go:115` hardcode `-z` tanpa toggle. Fix: toggle per tipe.

## Transfer time formula

```
transfer_time = data_size / effective_throughput
effective_throughput = min(nic, disk_read_iops*bk, disk_write_iops, ssh_compress_cpu)
overhead:
  + rsync file-walk O(n files): 100k file = puluhan detik
  + ssh encrypt: ~5-15% CPU single-core
  + zstd level 3 ~+20% wall; level 19 saturates CPU
  + SFTP per-packet: ~10-30% lebih lambat dari rsync
contoh: 100GB/10MB/s = ~2.8 jam; 100GB/100MB/s = ~17 mnt
ETA = remaining / measured_speedBPS (ProgressTracker sudah benar, progress.go:106)
```

# 6. Migration Pipeline

## State machine (rekomendasi)

```
Draft → Preflight → Discovery → PreparingTarget → Seeding → Transferring
  → Replicating → Verifying → AwaitingCutover → CuttingOver → Completed
                                                         ↓
                              Failed → RolledBack / NeedsManualIntervention
```

**Gap sekarang:** `AwaitingCutover`/`NeedsManualIntervention` tidak ada.
`trafficSwitchStage` return `nil` lalu auto-advance ke observe target tanpa
traffic. **Fix:** tambah state `AwaitingCutover` yang **pause**, butuh
konfirmasi operator (atau auto-cutover Phase 2 dengan fencing).

## Stage I/O + idempotency + checkpoint

| Stage | Output | Idempotency key | Checkpoint persist |
|-------|--------|-----------------|-------------------|
| discovery | SystemInfo | sourceId+targetId | TODO (in-memory) |
| analysis | depGraph | categories hash | TODO |
| preparation | provision states | component name | ✅ per-component |
| initial_sync | applied steps | step.ID (✅ StepStatusApplied) | ✅ per-category |
| live_replication | repl status | db name | TODO lag poll |
| traffic_switch | switch state | — | ❌ manual_required |

**CRITICAL:** `UpdateStageCheckpoint` zero caller → persist checkpoint per stage.

## Retry/rollback decision table

| Error category | Retry? | Rollback? |
|---------------|--------|-----------|
| TransientNetwork | ✅ 3x | ❌ |
| Auth | ❌ | ❌ NeedsManual |
| DiskFull | ❌ | ❌ |
| Incompatible | ❌ | ❌ NeedsManual |
| ChecksumMismatch | ✅ 1x | ❌ |
| CommandNotFound | ❌ | ❌ NeedsManual |
| TargetUnavailable | ✅ 5x | ❌ |

**Rollback otomatis JANGAN** jika: replikasi aktif (split-brain), cutover
sudah switch traffic, atau integritas DB belum diverifikasi.

# 7. Minimal Downtime Roadmap

## Phase 1 MVP (harus benar-benar selesai)

1. Fix bug kritis: split-brain rollback, MySQL Detect, Redis `|| true`,
   ExecWithStdin 30s, volume injection.
2. Container mode adapter (`ExecMode` + `docker exec -i`).
3. Dump/restore aman untuk PG+MySQL (streaming), no-timeout path.
4. Honest manual cutover state: `AwaitingCutover` yang pause.
5. Persist checkpoint per stage.
6. rsync untuk file/volume (ganti SFTP >1GB).

## Phase 2 — PostgreSQL live replication

- **Logical** (pub/sub): cross-major, subset, target writable. Missing sekarang.
- **Physical** (`pg_basebackup`): sudah ada (`replication.go:378`), same-version.
- MySQL **unseeded** sekarang (`replication.go:235`) — fix: seed dump dulu.
- Flow: seed (Phase 1 dump) → setup sub → poll lag → 0 → freeze writes
  (`freeze.go:146`) → final sync → promote target (`pg_promote`) → demote
  source → switch traffic → unfreeze.
- **Rollback:** demote target, source kembali primary. **Jangan `rm standby.signal`** (itu promote, bug `replication.go:428`).

## Phase 3 — MySQL/Mongo/Redis replication

| Engine | Realistis MVP? | Catatan |
|--------|---------------|--------|
| MySQL binlog | ✅ | fix unseeded, `Seconds_Behind_Master` |
| Redis REPLICAOF | ✅ | sudah real (`replication.go:434`) |

## Cutover flow detail

```
1. FreezeManager.Freeze() → read-only source (fence token)
2. WaitForCatchUp() → lag ≤ 0
3. Verify target health
4. TrafficSwitchEngine: DNS/proxy/LB/floatingIP/appConfig flip
5. Promote target (DB primary), demote source
6. Unfreeze target (writable)
7. Observe N min, auto-rollback jika error > threshold
```

## Rollback flow detail

```
1. Reverse traffic (→ source)
2. Demote target, source kembali primary
3. Unfreeze source
4. Data target dibiarkan (snapshot forensik, jangan drop)
KONDISI STOP: cutover > observation window + ada write ke target
→ split-brain → NeedsManualIntervention, jangan auto.
```

## Trade-off jujur

- Zero-downtime penuh butuh fencing (lease/lock distribusi). Tanpa itu,
  split-brain tak terhindarkan saat partition. **MVP realistis = minimal
  downtime (detik–menit), bukan nol.**
- Mongo replica set cutover kompleks (election); deferring ke Phase 3 jujur.
- Traffic switch otomatis butuh kredensial provider per-user; **manual
  cutover dengan checklist** lebih realistis untuk MVP opensource.
